## Prompt 4 · Reviews that work

```
Read CLAUDE.md. Turn the empty testimonials section into a working reviews feature: customers submit a review, Fitz approves it from his phone, and approved reviews appear on the site. Run d700-compose in diff mode for the new components (review form, review card, moderation page), using the same tokens and card patterns as today.

Rules that shape it (ACCC guidance on online reviews):
- publish every genuine customer review, good or bad. Decline only spam, reviews from people who haven't used the service, abuse, or anything that identifies a property's location or a person who hasn't agreed to be named.
- state that policy in one plain sentence beside the reviews and on the form
- never edit a review's words; no incentives; no star ratings in v1.0; no AggregateRating/Review schema.org markup (Google doesn't show review rich results for reviews a business hosts about itself)

Submission: a /reviews page, plus a "Leave a review" button in the home section.
- Fields:
  - first name and last initial
  - region (select from site.json "area")
  - property type (beef, dairy, sheep, mixed, lifestyle block, horticulture, other)
  - service used (select from site.json services)
  - review text, 20–800 chars
  - email (private, never shown)
  - "OK to publish this on the website" checkbox (required)
- Protection: honeypot, Turnstile, and 3 per day per IP.
- POST /api/reviews stores the review in Redis as pending, then emails Fitz "New review from {name}, {region}" with the full text and a link to the moderation page: ?id=…&exp=…&sig=… (HMAC-SHA256 with REVIEW_SECRET, 30-day expiry).

Moderation:
- Opening the moderation link (GET) only shows the review and two buttons: Publish, and Decline with a reason (spam / not a customer / abusive / identifies a location or person). It also offers an optional short public reply from Fitz. Gmail and Outlook link scanners open links automatically, so nothing may change on GET. The buttons POST to /api/review-action, which checks the signature and expiry again.
- Publishing adds the review to a Redis sorted set ordered by date. Declining records the reason. Neither deletes the original.

Display:
- GET /api/reviews returns published reviews, newest first, max 50, no emails, with Cache-Control: s-maxage=60, stale-while-revalidate=600.
- Testimonials already in site.json are baked into the HTML, so they show without JS. Fetched reviews are added beside them. Home shows the newest 3 and a "Read all reviews" link; /reviews shows all of them.
- Empty state: one card inviting the first review. If Redis isn't configured, /api/reviews answers {enabled:false} and the form is replaced with "Reviews open soon — call 0499 866 580".
- Leave a slot in the card layout for testimonial videos (Prompt 5 fills it).
- If site.json has google_review_url, add "Review us on Google" next to the form.

Tests:
- HMAC sign, verify and expiry
- a GET of the moderation link changes nothing
- a POST with a bad or expired signature returns 403
- the full flow against an in-memory store when the Redis env vars are absent locally (dev only — never in production)
- Playwright: submit → pending; approve on the moderation page → the review appears on /reviews and home; 390px layout; the whole form works keyboard-only

Commit, push, confirm the deploy, and write me a three-line note I can forward to Fitz explaining how approving reviews works.

## Prompt 5 · Videos (run this one on the computer that has the MP4s)

```
Read CLAUDE.md. Get Fitz's MP4 videos onto the site. The originals are in <PATH TO THE FOLDER>. Copy them into media-src/ (gitignored) and never commit video files.

Tools:
- ffmpeg/ffprobe. If missing: `winget install Gyan.FFmpeg` on Windows, `brew install ffmpeg` on macOS.

- BLOB_READ_WRITE_TOKEN: get it with `vercel env pull .env.local`, or ask me to paste it into .env.local.

Write scripts/media.mjs that, for each file:
1. Runs ffprobe and prints a table (duration, size, resolution, rotation, streams). Show me the table before encoding anything, and ask me for each clip's kind (work / drone / testimonial), title and one-line caption.
2. Encodes for the web: H.264 High, yuv420p, CRF 23, max 1280px on the long edge (1920 only for drone clips I mark), ≤ 30 fps, AAC 128k, -movflags +faststart.
3. Strips location and identifying data. The site promises "Location withheld", and phone and DJI footage carries GPS. Use -map 0:v:0 -map 0:a:0? -map_metadata -1 -map_chapters -1 -sn -dn. Re-probe the output and fail if any location tag, subtitle stream or data stream survives. Never upload DJI .SRT sidecars.
4. Makes a poster frame (WebP + JPG, 1280w) at a point I can override. For the drone band, optionally makes a silent ambient loop: ≤ 8 s, 960w, ≤ 1.5 MB.
5. Uploads to Blob as video/{slug}-{contenthash8}.mp4 (access public, contentType video/mp4, cacheControlMaxAge 1 year, no random suffix, never overwrite).
6. Appends an entry to content/media.json: id, kind, title, caption, description (for screen readers), src, poster, width, height, duration, bytes, captions (VTT URL or null) and transcript. Testimonials also need consent: true; refuse to publish a testimonial without it.

Before uploading, show me a contact sheet of a few frames per clip and ask me to check for:
- burned-in coordinates
- property names or signage
- number plates
- faces of people who haven't agreed
Blur or crop on request (ffmpeg boxblur on a region).

Ask me before publishing any clip that shows an animal being shot. Support an optional content_note field that shows over the poster until the visitor presses play.

Captions: if whisper is installed, draft VTT captions for clips with speech and show them to me to correct. Otherwise ask me for a transcript. Every testimonial video needs captions or a transcript.

Rendering (src/build.py reads content/media.json):
- the native <video controls preload="none" playsinline poster width height> element with <track kind="captions">. No autoplay with sound, no third-party player, and nothing downloads until the visitor presses play.
- gallery: video tiles inside the existing photo frames (registration ticks, "Location withheld" plate), with a play mark and the duration

Budgets: warn when a clip is over 25 MB. Before any video plays, the home page must weigh no more than it does now.

Verify with Playwright: no video bytes are requested on page load; posters load; the captions track is present; the keyboard can play and pause; the 390px layout holds; reduced motion stops the loop. Commit the manifest and code (no media), push, confirm the deploy, and tell me the total Blob size.
